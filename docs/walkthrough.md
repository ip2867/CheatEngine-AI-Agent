# 实战记录：用 AI agent 打通 Cheat Engine 训练关

这份文档不是功能介绍，是**打输过、找错过、被自己骗过之后留下的记录**。
每一条都标了它是在哪一步付出代价才换来的。

目标程序：Cheat Engine 自带的 `gtutorial-x86_64.exe`（Step 1 / Step 2）。

## 一、Step 1：换弹死局

### 现象

Step 1 的靶子有血量，玩家有弹药。屏幕上的弹药计数从 5 往下掉，打空后换弹。

按像素实测的干净序列：

```
弹药 1 → 血量 8
打一枪 → 弹药 5，血量 188   ← 回满了
打一枪 → 弹药 4，血量 142
打一枪 → 弹药 5，血量 98    ← 显示跳回 5，但血正常扣（显示 bug）
打一枪 → 弹药 3，血量 52
打一枪 → 弹药 1，血量 8
打一枪 → 弹药 5，血量 188   ← 又一轮
```

### 为什么这是死局

- 满血 188px ÷ 每发 46px ≈ **4.09 发**。
- 而**第 5 发正是触发换弹的那一发**，它不造成伤害，还把靶子治回满血。
- 所以 "打得更准" 永远差一发。

### 一个被误导很久的错误

"五下打死" 一度被理解成 "血量是 5"。这是错的，而且这个错误把后面所有
搜索都带偏了 —— 血量根本不是 5，它是 100（`0x015E4CB0 + 0x60`），
"五下" 只是 188px 轨道除以每发伤害的视觉效果。

**屏幕上的数字（弹药、血条宽度）和内存里的血量是两套量，不要互相代入。**

### 换弹是枪驱动的，不是定时

屏幕停在 `弹药 1 / 血量 8` 连续 12 次检查（约 5 秒）都不回血，再开一枪
立刻回满。所以不存在 "等它自己换弹" 的时间窗可以利用。

另外：换弹回血是**渐进动画**（8 → 152 → 188），而弹药计数是瞬时跳变。
抓帧抓到中间态是正常的，不是读数错误 —— 但必须能识别出来，否则会拿
中间态当稳定值做因果推断。

### 怎么破

题解文章里那句关键话：

> 扫到一半会发现问题：界面显示 3 的时候，候选地址里已经出现 0 了。
> 这说明**显示值和内存值不是同向的**。恢复满弹，改成从 0 开始按
> "增加的值" 重扫，才命中真正的地址。

也就是说弹药字段是**反向映射**的（显示 0 → 内存满）。命中地址后按满弹值
锁定，装弹流程就永远不触发。实操上这一关是这么过的。

### Step 1 血量地址：一个「能改但没用」的教训

用 unknown → decreased → increased 找到过 `0x167C1B0`（float 76.0）：

- 写 38.0 → 血条立刻从 142px 掉到 72px（**正好一半，188/76 ≈ 2.47 px/点**）
- 写 0.0 → 锁了 201 次 / 4.8 秒，窗口始终 `Step 1`，游戏**不判定死亡**
- 打一枪 → 值自己跳回 76.0
- 邻居：`+0x00` 血量、`+0x04` 0.25、`+0x08` 0.05、`+0x0C` 0.008（伤害百分比）
- 整个堆里没有任何指针指向它

**它是每帧被游戏重写的显示副本。** 血条跟着它变，是因为游戏用它在画血条，
不是因为它就是血量的权威。写 0 不死的直接原因：死亡判定读的是另一处。

## 二、差分收窄：真正有效的那一步

限制到游戏真实可写堆区（约 123 MB）之后：

```
33,632,256  unknown 基线
  → 116,873  打一枪 decreased
  →   2,183  跨换弹 increased     ← 一步砍掉 98%
  →      31  值落在 100..250
```

**核心洞察：`decreased` 筛不掉计时器。** 帧计数器、粒子计时器、动画时钟
永远在递减，任何 `decreased` 过滤都留得住它们。只有 "换弹回满" 那一刻的
`increased` 能把它们一次清掉。

这也解释了为什么前面几轮 `decreased` 收窄都在几百个候选上打转。

### 假收敛的根因

`scan_next` 比较的是**扫描时刻记录的值**，而 `read` 返回**实时值**。
两者之间发生变化的字段会主导幸存集，而不是你要找的字段。

正确的收窄必须用实时读：

```
scan_results 分页 → 逐地址 read → 只留 live 且等于目标值的
```

`scan_results` 的返回里本来就有 `live` / `staleReason` / `changedSinceScan`，
直接用，别自己推断。

### 结构性筛选比数值筛选更硬

当数值筛选还剩上千个，先按**形状**砍：

| 形状 | 结论 |
|---|---|
| 固定步长（`0x78`）成对同值 | 数组，先剔 |
| 换弹后精确回到初值 | 副本，不是权威 |
| 整个堆里没有指针指向它 | 没人写它，是镜像 |

这一步曾把 372 个候选一次砍到 40 个，而 40 个全是同一片副本数组。

## 三、dword / float 的类型赌注

Step 1 用 float 找到了血量副本，于是 Step 2 一路按 float 找玩家血量，
**连续五轮全线落空**，最后是用户手动在 CE 里用「浮点数 + 减少的值」
筛出 `0167C1B0` 才发现 —— 而 Step 2 的玩家血量 `0x015E4D10` 是**整数**。

**教训**：类型假设决定成败。扫之前先回答「代码拿这个值做什么」：

- 血条按比例画 → float
- 每次扣固定伤害的计数器 → dword

答不出来就跑**两个独立假设**，别赌一个。

一个具体的坑：`write` 的 `expect` 乐观锁**不按目标类型解码**。给 float 地址
传 `expect=76.0` 会被判 `STALE: expected 76 at 0x167C1B0 but found 1117257728`。
必须传原始位模式：

```python
import struct
def rb(x): return struct.unpack("<I", struct.pack("<f", float(x)))[0]
```

## 四、断点：被误判为「不支持」的几天

### 错误结论

「CE 7.7 在本机 `debug_breakThread` 停不住目标，硬件断点完全不可用。」

### 真因

两个事实，缺一个都复现不了：

1. **`set_breakpoint` 内部会调 `debugProcess()` 附加调试器，`bps_arm` 不会。**
   所以 `bps_arm` 装出来的断点 `ceHasBreakpoint: true`、`hitCount` 恒为 0 ——
   断点确实装上了，调试器压根没附加。

   ```
   before: {'breakpoints': {}, 'canBreak': False, 'debugging': False}
   set_breakpoint(addr="0x167C1B0", size=4, trigger="write")
   after:  {'breakpoints':[{'addr':'0x167C1B0','bpId':'bp1','hits':0}],
            'canBreak': True, 'debugging': True}
   ```

2. **调试器会在两次调用之间自己掉回 `canBreak: false`。**
   要抓开火那一瞬间的写入，必须**另开一个连接**循环检查并重装：

   ```python
   while not stop.is_set():
       st = cl2("debug_state")
       if isinstance(st, dict) and not st.get("canBreak"):
           cl2("set_breakpoint", addr=..., size=4, trigger="write", label="hp")
       time.sleep(0.05)
   ```

   实测：`armed 1 times`，`bp2.hits = 82`。

### 踩过的坑

- `bp_hits` 必须显式带 `bpId`，否则 `NOT_FOUND: unknown bpId: nil`。
- `read_registers` 在没有活动断点时返回 `DEBUGGER_NOT_ATTACHED`。
- **监听窗口必须比人的反应时间长。** 75 秒和 150 秒两次都因为用户开枪
  落在窗口外而 0 命中，白白得出 "断点没用" 的结论。

## 五、写进去不等于留住

`write` 返回 `verified: true` 只证明**字节落地并回读一致**，从不证明
游戏保留了它。三个例子：

| 地址 | 看起来像什么 | 实际是什么 |
|---|---|---|
| `0x167C1B0` | float 血量 76.0，写一下就变血条 | 每帧被重写的显示副本 |
| `0x6EF0129` + 20 槽 | 每枪精确等步长，换弹回初值 | 副本数组 |
| `0x15E4BD0` | 敌人结构体里的 `+0x60` | 血条根本不读它 |

写单槽被立刻覆盖（回读到 `540163`，正好是下一个槽的值）；写 20 槽全 0
`verified: True` ×20，血条 188 → 188 不动。

**判据不是「写进去了没」，是「1.5 秒后还在不在，改它屏幕动没动」。两个
条件都要。**

如果写进去被覆盖，别再找「更好的地址」，直接在它上面下写断点读 IP：
要么它是镜像，要么它就是真字段而权威在上游。

## 六、Step 2：区分敌我的代码注入

### 结构体布局（实测，共用虚表 `0x2B4478`）

```
0x015E4B70  +0x24=+0.205  +0x28=-0.8  +0x60=200  +0x64=200  +0x70=1   ← 敌方
0x015E4CB0  +0x24= 0.000  +0x28=+0.8  +0x60=血量  +0x64=100  +0x70=0   ← 我方（唯一）
0x015E4D50  +0x24=-0.205  +0x28=-0.8  +0x60=衰减   +0x64=200  +0x70=1   ← 敌方
```

- 基址间距 `0x140` / `0xa0`，**不是等步长**。
- **`+0x70` 才是阵营标志**（我方 0 / 敌方 1）。
- `+0x24` 只是碰巧相关的 float，**不能用它做判据**。

### 共享扣血函数

```asm
100042D10  48 89 C8    mov rax,rcx
100042D13  29 50 60    sub [rax+0x60],edx    ; 血量 -= 伤害
100042D16  C3          ret
100042D17  00 00 ...                          ; 9 字节零空隙
100042D1F  53 56 48 8D 64 24 D8 48            ; ← 后面是另一个函数，不能覆盖
```

断点抓到 `rcx=0x15E4CB0`（玩家）、`rdx=2`（伤害）。`.text` 段
`0x100001000`–`0x10023C000`，代码洞（1256 字节连续零）在 `0x10023BB18`。

### 注入体

```
hook:  E9 03 8E 1F 00 90 90          ; jmp 到代码洞，补 2 个 nop
cave:  48 89 C8                      ; mov rax,rcx
       83 78 70 00                   ; cmp dword [rax+0x70],0
       75 03                        ; jne +3  → 敌方，跳过 ret
       C3                           ; ret      → 我方，直接返回（无敌）
       90 90                        ; nop 填充
       29 50 60                     ; sub [rax+0x60],edx（原指令）
       C7 40 60 00 00 00 00         ; mov dword [rax+0x60],0（敌方一击清零）
       C3                           ; ret
```

结果：左敌一枪秒杀，玩家无敌。

**为什么必须用 `[rax+0x70]` 而不是 `[rax+0x24]`**：
`+0x24` 是 float，`cmp dword [rax+0x24], 0` 比较的是位模式
`0x3E51EB85`，永不相等，会把所有对象都判成敌方。这个 bug 第一次写的时候
就犯了。

### 代价：完整性检测

注入成功后，窗口标题立刻变成：

```
Step 2 (Integrity check error)
```

在这个状态下，**整个战斗循环冻结**：子弹穿过敌人不扣血、敌方开火无效、
血条不动。这看起来跟 "瞄不准" 一模一样，为此浪费了一小时去追几何问题
（右敌中心 x=966.5，玩家 x=799.5，垂直差 985px，需要 9.6° 偏角 ——
这个测量本身是对的，但当时根本不是几何的问题）。

恢复：还原 `0x100042D10` 原 7 字节 + 代码洞清零，标题回到 `Step 2 `，
**不需要重启游戏**。

所以：实验可逆，但不能留在那里。

### 桥的一个真 bug（已修）

`write_readonly` 原来调用全局 `virtualprotect` —— 这个名字在 CE 7.7 中
**不存在（nil）**，所以该命令每次都失败。autorun 探测器实测：

```
virtualprotect      nil
virtualProtectEx    nil
VirtualProtectEx    nil
VirtualProtect      nil
setMemoryProtection function     ← 存在，但对未 open 的进程无效
protectMemory       nil
getMemoryProtection function     ← 返回 {w,r,x}，没有 protect 字段
writeBytes          function
```

修法：删掉桥里两处只读拦截（`handlers.write` 与 `handlers.write_bytes`，
**两处都要删**，只删一处时 `write_bytes` 仍报 `PERMISSION_DENIED`），
让 CE 自带的 `writeBytes` 自己去处理保护。改后需**重启 CE** 生效。

## 七、像素通道：唯一能用的观测手段，也是骗过我最狠的一次

### 抓图

`PrintWindow`（含 `PW_RENDERFULLCONTENT=0x2`）在这个构建上**返回全黑**。
唯一有效路径是从**屏幕 DC** 在客户区原点 `BitBlt`：

```python
pt = POINT(0, 0); ClientToScreen(hwnd, pt)
screen = GetDC(0)
BitBlt(mem, 0, 0, w, h, screen, pt.x, pt.y, SRCCOPY)
```

所以窗口必须在前台。抢前台的可用序列是
`AttachThreadInput` + `ShowWindow(SW_RESTORE)` + `BringWindowToTop` +
`SetForegroundWindow` + `SetActiveWindow`；单用 `SetForegroundWindow` 会输。

**护栏**：`GetForegroundWindow() != hwnd` 时直接放弃，不存帧。
抓两次（间隔 0.8s）取墨多的一张。正常帧 19–33 KB，半绘制帧 744 KB ——
744 KB 那种曾被当成有效帧接受了很久。

### 数字识别

手写模板只有 0.6–0.8 分，读出来是自信的垃圾。有效的是**墨量查表**，
表从已知真值的帧里抠：

```
ink 140 → '5'      ink 136 → '3'      ink 128 → '4'      ink 108 → '1'
```

墨量分不开 5 和 6，位图比较只留作这两个的 tiebreak。**永远不要手画模板。**

数字画在血条里，掉血时血条左边界会吃掉最左字形。要能识别，而不是硬读：

```python
clipped = any(row[0] for row in mask[:4])
```

只有第一个字形允许「低分 + 被裁」；其余字形低分即整帧作废，防半帧。

### 弹药框

朴素搜索会把说明面板的大红圆和数字并成一个 100px 无用块。有效的做法：

1. 只扫 `x >= 0.55*w`、`y >= 0.80*h`
2. 行红像素分段，`gap > 6` 切
3. 取**最下方**的计数器尺寸 band（`22 ≤ h ≤ 44`）
4. band 内列直方图，`gap > 4` 切字形
5. 取**最右**字形，`14 ≤ w ≤ 70`

框**不是稳定的**：一次会话里从 `x1552` 漂到 `x1430`，因为说明面板显隐会让
整条底部 HUD 在 y 方向平移约 86px。每帧重算，常量只做后备。

### 颜色分工

左敌血条是**绿色**（`g>120, r<100, b<100`），右敌是**蓝色**
（`b>120, r<100, g<100`）。只认绿色的检测器会把蓝条报成「不存在」，
而「不存在」会被读成「敌人已死」。

## 八、结构形状扫描：两个小时缩短到一秒

### 起因

前面所有找血量的尝试都是**按值**筛：`unknown` → `decreased` → `increased`。
这条路能走通（第一步砍了 98%），但它反复撞同一堵墙：

> 值在变的东西太多了。计时器、帧计数、每个对象里的十几个浮点参数，
> 全都随屏幕变化。

而且它的成本结构是错的：一次扫描要跨几十万次管道往返，
收敛到几十个候选之后，还得逐个写入、截图、看血条 —— 189 个候选试到第 120 个时，
**游戏进程被拖死了**。

### 换判据：不看值变不变，看形状像不像

血量在一个实体结构里长这样：

```
+0x00  hp    当前血量
+0x04  max   血量上限
```

这两个 dword 相邻，而且必然满足 `hp <= max`。这不是数值规律，是**逻辑约束** ——
任何计数器、计时器、浮点参数都不会「碰巧」满足它。

于是问题从「哪些值在按血条的方向变」变成「哪些相邻 dword 对长得像血量」，
后者可以**一次扫完整个堆**。

### 工具：`find_struct`

关键在于扫描发生在 CE 内部，不是逐地址问回来：

```lua
-- 64 KiB 一个块，块内本地解析，块间留 4 字节重叠防止配对跨块
local tabs = readBytes(addr, want, true)
-- 两个判据：max 在允许集合里，且 hp <= max
local okPair = anyMax and (mx > 0) or (maxhpSet[mx] == true)
if okPair and requireHpLeMax and hp > mx then okPair = false end
```

实测（4 MB 窗口，`gtutorial` Step 2）：

| 判据 | 候选数 |
|---|---|
| 只要求 `max` 在 `{100,200,300,500}` 里 | **159** |
| 再加 `hp <= max` | **6** |

**一个约束砍掉 26 倍，而且被砍掉的全是 `hp=301925169 max=100` 这种明显垃圾。**
三个真实体（两个敌人 + 玩家）一个没丢，耗时 **0.9 秒**。

### 为什么它比差分强

| | 差分收窄 | 结构形状 |
|---|---|---|
| 需要的动作 | 每轮都要打一枪 / 等换弹 | 不需要任何操作 |
| 成本 | 每轮几十万次往返 | 一次调用 |
| 计时器干扰 | 主要干扰源，必须靠换弹回血才砍掉 | 天然免疫（`hp>max`） |
| 命中后 | 还要写入验证 | 直接是实体，可读周围字段 |

差分仍然有用 —— 它是**不知道结构时**唯一的路。但一旦知道
「这是一个血量对」，就该立刻换成形状扫描，而不是继续收敛数值。

### 前一个思路错在哪

我一开始想用**虚表指针**筛实体：扫整个窗口找 `vtable=0x2B4478`。
结果是 1.4 MB 里只有 2 个，右敌始终找不到 —— 因为我默认
「所有实体都在同一个虚表下」，而这不是事实。

**形状判据比身份判据稳**：虚表值可能变（多态、不同工厂），
但 `hp <= max` 是游戏逻辑本身决定的。用会变的东西当锚点，就是给自己埋坑。

## 九、批量读：逐地址轮询不是慢，是会失败

`read_memory` 一次读一个值。找遍 4 MB 的每个 dword，是**一百万次往返**。

这不是「慢一点」，是：
1. 任何工具超时都跑不完（`MCP` 默认超时 60 s，实际测下来 3 分钟没动）；
2. 每次往返都在目标进程上做一次读 —— **实测把游戏轮询到崩溃过**。

所以桥里必须有批量读：

```lua
handlers.read_bytes = function(args)
  local count = math.min(tonumber(args.count) or 256, 262144)
  local tabs = readBytes(addr, count, true)
  -- readBytes 会在页边界提前停，必须报告实际读到的长度
  return ok({ requested = count, returned = #tabs, hex = ... })
end
```

MCP 侧只加一行装饰器就暴露出去。**用 `returned` 推进，不要用 `requested`
—— 跨页会提前停，按请求长度推进会让每一页边界变成一个数据黑洞。**

配上它之后，同样的全堆扫描从「跑不完」变成 **0.9 秒**。

## 十、没做到的部分（如实记录）

### 右敌血量字段（第一轮）

最初扫 `0x01500000..0x01640000`（1.4 MB），用虚表判据只找到 2 个实体
（左敌尸体 + 玩家），右敌始终不在里面。当时判断「右敌不在这窗口」，
**这个判断是错的** —— 用结构形状扫描后，三个实体一次全部出现：

```
0x015E4B70  hp=200  max=200   ← 敌人 1
0x015E4CB0  hp=100  max=100   ← 玩家
0x015E4D10  hp=200  max=200   ← 敌人 2
```

间距 `0x140` 和 `0xA0` 与历史记录完全一致。**它们一直都在，是判据错了。**

### 代码注入的代价

为了让一枪秒杀，把共享扣血函数 `0x100042D10` 改成「敌方直接清零」：

```asm
cmp  dword [rax+0x70], 0     ; 阵营：0 = 玩家，1 = 敌人
je   skip
mov  dword [rax+0x60], 0     ; 敌人血量清零
```

左敌确实一击就死。但窗口标题立刻变成 **`Step 2 (Integrity check error)`**，
战斗循环冻结 —— 子弹穿过不扣血，敌方开火无效。

**这就是「打不中右敌」的真因**：不是瞄准几何算错了，是游戏已经停了。
判断一个「打不到」的问题之前，先确认游戏还在跑。

### 像素管线的一个静默错误

抓图用 `BitBlt` 从**屏幕 DC** 取像素（这个构建上 `PrintWindow` 全黑）。
但屏幕上有别的东西时，抓到的是**拼贴图** —— 一次「抓通关截图」实际存下来的是
一个聊天窗口。

原来的护栏只检查 `GetForegroundWindow() == hwnd`，
而**处于前台不代表没被遮挡**（悬浮层、通知、另一个置顶窗口都可能在上面）。
补上的检查是遍历 z 序，看客户区矩形上有几个别的可见窗口：

```python
u.EnumWindows(_cb, 0)     # 收集所有与客户区相交的其他顶层窗口
if found: return True, 'obscured by ' + '; '.join(found[:3])
```

抓到遮挡就**拒绝保存并删掉旧图**，而不是存一张看起来像样的错误画面。
一张自洽的错图比没有图更危险，因为下游全都信它。

## 十一、如果重来一次，顺序是这样

1. `memory_regions(writable=true)`，把扫描限制在真实堆（约 123 MB，不是 4 GB）。
2. **先 `find_struct` 找形状**，别一上来就差分。知道要找「相邻 hp/max 对」
   的时候，一次调用就够，不需要打任何一枪。
3. 不知道结构时才用差分：`unknown` → `decreased` → **跨回满 `increased`**，
   这一步砍 98%。
4. 用 `cset_page` 的实时值收窄，不用 `scan_next` 的快照。
5. 写入被覆盖 → 下写断点读 IP，别换地址。
6. 断点用 `set_breakpoint`（会 `debugProcess`），并另开连接重装。
7. 改代码前先确认有没有完整性检测；改完能还原。
8. **改完代码先看窗口标题和游戏是否还在跑**，再怀疑自己的瞄准。
9. 屏幕和内存两个通道，两边都对上才算结论。
10. 抓图前确认屏幕没被遮挡 —— 前台不等于可见。
